# g9s-builders

Сборочные машины для узлов governetics. Разработчик отправляет сборщику коммит своего репозитория, сборщик
собирает его по рецепту и отдаёт артефакты: архивы образов, контрольные суммы, журнал, сводку тестов.

Сборщик **не ходит в репозитории сам**: исходники приходят к нему git-bundle'ом от разработчика. Так он не зависит
ни от хостинга кода, ни от VPN, а коммит в bundle'е — проверяемый хеш содержимого: собирается ровно то, что названо.

Репозиторий намеренно **ничего не знает о проектах**, которые собирает: здесь только инструменты, раннер и
sidecar'ы. Рецепты и шаблоны конкретных проектов живут у их владельцев и доезжают на сборщик файлами проекта
панели (см. «Рецепты»).

## Устройство

```
stacks/<stack>/Dockerfile       образ сборщика: инструменты стека + раннер
runner/g9s_runner.py            HTTP-раннер (python3, только стандартная библиотека)
runner/summarize_tests.py       сводка surefire/failsafe → test-summary.txt (для рецептов Maven)
client/g9s-build                команда разработчика: bundle → сборка → артефакты
sidecars/<name>/Dockerfile      вспомогательные контейнеры (например, клиент OpenVPN)
deploy/governetics/*.yml        образец шаблона проекта для панели governetics
.github/workflows/publish.yml   публикация образов в ghcr.io: тег <имя>/vX.Y.Z или ручной запуск
```

| Образ | Что внутри |
|---|---|
| `ghcr.io/ancientglider/g9s-builders/java` | JDK 25 (Temurin), Node 24, Docker CLI + buildx, git, python3, `LANG=C.UTF-8` |
| `ghcr.io/ancientglider/g9s-builders/openvpn` | клиент OpenVPN (Alpine); профиль и логин — файлами проекта |

Образы собираются только для `linux/amd64`. Демон Docker для сборок — отдельный контейнер `dind` в том же проекте
панели (свой том образов, сокет хоста не нужен). Привилегированный контейнер `dind` — это по сути root на узле:
ставьте сборщик на узел, которому это можно.

## Разработчику: как собрать

1. Получите у оператора адрес сборщика, имя рецепта и свой токен. Положите токен в
   `~/.config/g9s-builders/token` (права `0600`) либо в переменную `G9S_BUILDER_TOKEN`.
2. Возьмите `client/g9s-build` в `PATH`.
3. Из каталога своего репозитория:

```bash
g9s-build --url https://builders.example.org --recipe <рецепт> origin/master
```

Команда находит, каких коммитов у сборщика ещё нет, шлёт только их, ждёт сборку, печатая её журнал, и складывает
артефакты в `./g9s-out/<рецепт>-<sha7>/`. Параметры рецепта — `-p ключ=значение`; `--no-wait` — только поставить в
очередь. Переменные `G9S_BUILDER_URL` и `G9S_BUILDER_RECIPE` заменяют ключи `--url` и `--recipe`.

Один сборщик делает одну сборку за раз, остальные ждут в очереди. Артефакты хранятся для последних пяти сборок
каждого рецепта (`G9S_KEEP_BUILDS`), журналы и сводки — всегда.

## Pull-режим: сборка по тегу

Если у сборщика есть доступ к репозиторию (VPN, deploy token), он может ходить за исходниками сам. Файл проекта
`repo.<рецепт>` (в `G9S_RECIPE_FILES`):

```
url=https://git.example.org/group/project.git
tags=^v            # регулярное выражение на имя тега; пусто — по тегам не собирать
poll=60            # период опроса, секунды
```

Учётные данные — файл `git_credentials.<рецепт>` (или общий `git_credentials`) со строкой `логин:пароль`
(для GitLab — deploy token с `read_repository`). Раннер раз в `poll` секунд делает `git ls-remote --tags`;
при первом опросе запоминает существующие теги и ничего не собирает, дальше каждый **новый** тег под шаблон
ставится в очередь (`trigger: tag:<имя>`, `submitted_by: tag-poll`). Любой ref можно собрать руками:
`g9s-build --pull <ветка|тег|sha>` → `POST /api/builds?recipe=…&ref=…`. Состояние опроса — в `/api/health`
(`repos`: последний опрос, последняя удача, ошибка). Загрузка bundle работает параллельно.

## API раннера

Все запросы, кроме `/api/health`, — с заголовком `Authorization: Bearer <токен>`.

| Запрос | Ответ |
|---|---|
| `GET /api/health` | состояние: текущая сборка, длина очереди, рецепты, есть ли файл токенов |
| `GET /api/recipes` | список рецептов |
| `GET /api/repos/<recipe>/tips` | до 50 коммитов, которые у сборщика уже есть (новые первыми) — чтобы прислать дельту |
| `POST /api/builds?recipe=…&commit=<sha40>[&p_<ключ>=…]`, тело — bundle (можно пустое, если коммит известен) | `202 {id}`; `422 commit_unknown` — пришлите bundle с коммитом под ссылкой `refs/g9s/upload` |
| `POST /api/builds?recipe=…&ref=<ref>[&p_<ключ>=…]` | pull-режим: раннер сам делает fetch; `202 {id, commit}`; `422 repo_not_configured` / `fetch_failed` |
| `GET /api/stats?recipe=…` | медианы длительности сборки и стадий по успешным сборкам |
| `GET /api/builds[?recipe=…&limit=…]` | последние сборки |
| `GET /api/builds/<id>` | карточка: статус, стадия и таймлайн стадий, признак «нет вывода N с», время, кто поставил, триггер, артефакты с `sha256` |
| `GET /api/builds/<id>/log?from=<байт>` | хвост журнала; заголовки `X-Log-Size`, `X-Build-Status` |
| `GET /api/builds/<id>/artifacts/<имя>` | файл |
| `POST /api/builds/<id>/cancel` | снять с очереди или прервать |

Страница `/ui` — список сборок, текущая стадия, живой журнал и артефакты; вход токеном (cookie браузера).
Рецепт сообщает стадию строкой в файл `$G9S_STAGE`; молчание дольше `G9S_SILENCE_WARN` (600 с) помечается,
дольше `G9S_SILENCE_KILL` (по умолчанию выключено) — прерывает сборку.

Статусы: `queued` → `running` → `succeeded` / `failed` / `cancelled` / `timeout` (`G9S_BUILD_TIMEOUT`, 2 часа по
умолчанию). Тело загрузки — до `G9S_MAX_UPLOAD_MB` (512).

## Рецепты

Рецепт — скрипт `bash`, который раннер запускает в корне выкаченного коммита. Он читает `G9S_SRC`, `G9S_COMMIT`,
`G9S_SHA7`, `G9S_PARAM_*` (параметры `-p` клиента, ключ в верхнем регистре), пишет артефакты в `G9S_OUT` и
завершается `0` при успехе; всё, что он печатает, попадает в `build.log`. Docker доступен через `DOCKER_HOST`.
Для сводки тестов Maven в образе есть `/opt/g9s/runner/summarize_tests.py <корень> --gate "<итог>" --command "<команда>"`.

Два источника рецептов:

- **общие** — каталоги `<G9S_RECIPES>/<имя>/build.sh` в образе (в этом репозитории их нет);
- **проектные** — файлы `recipe.<имя>` в `<G9S_RECIPE_FILES>` (`/etc/g9s/files`): объявляются в шаблоне проекта
  панели ключом `files` с `consumers: [runner]` и доезжают на узел как настройка. Рецепт хранится у владельца
  проекта, в образ и в этот репозиторий не попадает.

## Оператору: установка на узел governetics

1. Образы: тег `java/vX.Y.Z` или `openvpn/vX.Y.Z` в этом репозитории (либо ручной запуск workflow `publish` с
   именем и версией) → `ghcr.io/ancientglider/g9s-builders/<имя>:vX.Y.Z`.
2. Панель → «Registry»: источник `https://ghcr.io`, маршрут `ancientglider` → этот источник; для `docker:28-dind` —
   маршрут `docker` → Docker Hub.
3. Проект (`docker-compose`, продвижение `manual`) по образцу
   [deploy/governetics/builders.compose.yml](deploy/governetics/builders.compose.yml): свой шаблон держите у себя,
   в него добавьте ключи `recipe.<имя>` и, если сборке нужна закрытая сеть, sidecar `vpn`.
4. На узле → «Настроить»: файл `tokens` — строки `имя=токен` (токен: `openssl rand -hex 24`), файлы рецептов, при
   VPN — профиль и логин. Развернуть.
5. Смена версии образа: править тег в шаблоне недостаточно — рендер compose не меняется; при «Развернуть» задайте
   версию явно (`image_overrides: {"runner": "vX.Y.Z"}` в API либо версия в форме).
6. Снаружи — edge с TLS на порт `8181` узла; тело запроса до ~100 МБ, таймаут загрузки — минуты.
7. Проверка: `curl https://<адрес>/api/health` → `"tokens_file_present": true` и список рецептов; затем `g9s-build`.

Код сборки видит сеть, в которой стоит узел. Если узел в доверенной LAN, ограничьте выход контейнеров проекта
правилом `DOCKER-USER` на хосте (разрешить интернет, запретить локальные подсети) — панель этого не делает.

## Новый стек или sidecar

Стек — каталог `stacks/<имя>/Dockerfile` с инструментами и раннером (повторите хвост `stacks/java`). Sidecar —
`sidecars/<имя>/Dockerfile`; контекст сборки у всех — корень репозитория.
